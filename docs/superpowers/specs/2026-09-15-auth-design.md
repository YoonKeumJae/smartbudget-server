# 사용자 인증 설계

확정일: 2026-09-15

이 문서는 사용자와 합의한 인증 요구사항과 구현 시 지켜야 할 동작을 정리합니다. 서버 구현 완료를 의미하지 않습니다. API 경로, 요청·응답 스키마, 모듈 배치와 배포 주소에 따른 쿠키 설정은 구현 계획에서 구체화합니다.

## 1. 목적과 범위

사용자가 회원가입 후 아이디와 비밀번호로 로그인하고, 자신의 데이터에만 접근할 수 있도록 합니다. 클라이언트는 안드로이드 앱과 웹입니다.

- Python과 FastAPI로 HTTP 서버를 구현합니다.
- PyJWT로 액세스 JWT를 발급하고 검증합니다.
- 파일 기반 SQLite와 SQLAlchemy로 사용자와 로그인 상태를 저장합니다.
- 로컬 `.env` 및 시스템 환경 변수로 기밀 정보와 서버 설정을 지정합니다.
- 별도 캐시 서버나 메모리 세션 서버는 추가하지 않습니다.
- 서버 API와 클라이언트의 인증 연동 규칙을 다룹니다. 앱·웹 화면 구현은 포함하지 않습니다.
- 초기 버전에서는 이메일 수집, 이메일 인증, 비밀번호 복구 기능을 제외합니다. 비밀번호를 잊은 사용자가 스스로 계정을 복구할 수 없습니다.

## 2. 아이디와 비밀번호

### 아이디

| 항목 | 규칙 |
| --- | --- |
| 길이 | 4~12자, 양 끝값 포함 |
| 허용 문자 | ASCII 영문 `A–Z`, `a–z` 및 숫자 `0–9` |
| 대소문자 | 구분하지 않음 |
| 조합 | 영문과 숫자를 반드시 함께 포함할 필요 없음 |
| 그 외 문자 | 공백, 한글, 밑줄, 기타 특수문자 모두 거부 |

아이디는 소문자로 정규화해 저장하고, 회원가입 중복 검사·로그인·실패 횟수 집계에 같은 규칙을 적용합니다. `User123`과 `user123`은 동일한 아이디입니다. 정규화한 아이디에 DB 고유 제약을 적용해 동시 가입에서도 중복을 막습니다.

### 비밀번호

| 항목 | 규칙 |
| --- | --- |
| 길이 | 8~20자 고정, 양 끝값 포함 |
| 영문 | ASCII `A–Z`, `a–z` |
| 숫자 | `0–9` |
| 특수문자 | `!@#$%^&*_-+=?` |
| 조합 | 영문·숫자·특수문자 중 두 종류 이상 필수 |
| 대소문자 | 구분함 |
| 그 외 문자 | 공백·한글을 포함해 모두 거부 |

대문자와 소문자는 모두 영문 한 종류로 계산합니다. `Abcdefgh`는 거부하고 `Abcdef12`, `Abcdefg!`, `1234567!`는 허용합니다. 세 종류를 모두 포함해도 됩니다.

비밀번호의 대소문자를 바꾸거나 공백을 제거하거나 길이를 잘라내지 않습니다. 원문을 검증한 뒤 해시 처리합니다. 특수문자 목록은 제품의 입력 정책이며, 목록 밖 문자가 본질적으로 위험하다는 의미는 아닙니다. 입력을 SQL이나 명령어에 직접 이어 붙이지 않습니다.

비밀번호 원문은 저장하거나 로그에 출력하지 않습니다. Argon2id 기반 라이브러리로 해시 생성·검증을 처리하며, 소금값 생성은 라이브러리에 맡깁니다. 해시 연산의 메모리 비용은 서버 용량을 고려해 정하되 비밀번호 보호를 제거하지 않습니다.

## 3. 로그인 실패와 재시도 제한

- 존재하지 않는 아이디와 비밀번호 불일치는 같은 오류 안내를 사용합니다: `아이디 또는 비밀번호가 올바르지 않습니다.`
- 동일 계정의 최근 5분간 로그인 실패가 10회에 도달하면 해당 시점부터 3분간 로그인을 제한합니다.
- 아이디 대소문자를 바꿔도 같은 실패 집계에 포함됩니다.
- 제한 중에는 올바른 비밀번호로도 로그인할 수 없습니다.
- 제한 중 추가 요청으로 제한 종료 시각을 연장하지 않습니다.
- 정상 로그인 또는 제한 해제 후 실패 횟수를 초기화합니다.
- 제한 여부로 계정 존재가 드러나지 않도록, 존재하지 않는 아이디의 응답·제한 처리도 일관되게 설계합니다.
- 실패 집계와 차단 상태는 SQLite로 관리하고, 동시 요청에서 횟수 누락이나 제한 우회가 생기지 않게 처리합니다. 만료된 기록은 정리하고 사용자 입력으로 기록이 무제한 누적되지 않도록 구현 계획에서 보관 방식을 정합니다.

## 4. 토큰과 로그인 세션

| 항목 | 동작 |
| --- | --- |
| 액세스 토큰 | PyJWT로 발급하는 JWT, 기본 유효기간 15분 |
| 리프레시 토큰 | 액세스 토큰을 재발급받기 위한 비밀 증표 |
| 로그인 유지 기한 | 최초 로그인 시점부터 30일 |
| 갱신 | 리프레시 토큰 사용 시 새 토큰으로 교체 |
| 기한 연장 | 갱신으로 최초 로그인부터의 30일 기한을 연장하지 않음 |
| 재사용 감지 | 이미 교체된 리프레시 토큰이 다시 사용되면 해당 로그인 세션 폐기 |
| 세션 분리 | 웹과 안드로이드 로그인 세션을 별도로 관리 |
| 로그아웃 | 현재 세션을 즉시 폐기하고 클라이언트 토큰 제거 |

로그인 성공 시 세션과 두 토큰을 발급합니다. 액세스 토큰이 만료되면 클라이언트가 리프레시 토큰으로 갱신하므로 사용자가 15분마다 비밀번호를 입력할 필요는 없습니다. 30일이 지나거나 세션이 폐기되면 다시 로그인해야 합니다.

리프레시 토큰 원문은 DB에 저장하지 않고 해시로 저장합니다. 교체된 토큰의 재사용을 식별할 수 있는 정보도 유지합니다. 교체와 이전 토큰 무효화는 하나의 트랜잭션으로 처리하며, 클라이언트는 같은 세션에서 갱신 요청을 중복 실행하지 않아야 합니다.

보호된 요청마다 JWT뿐 아니라 SQLite의 세션 유효 상태를 확인합니다. 이 확인으로 로그아웃 후에는 액세스 토큰의 만료 전이라도 요청을 거부합니다. 한 세션의 로그아웃은 다른 세션을 종료하지 않습니다.

## 5. 웹·안드로이드 보관 방식

### 웹

- 액세스 토큰은 페이지 메모리에 보관하고 보호된 요청에 전달합니다.
- 리프레시 토큰은 `HttpOnly`·`Secure` 쿠키로 전달합니다. 장기 토큰을 `localStorage`에 저장하지 않습니다.
- 페이지 새로고침 후에는 리프레시 쿠키로 액세스 토큰을 다시 받습니다.
- 쿠키를 사용하는 갱신·로그아웃 요청에는 CSRF 방어를 적용합니다.
- `SameSite`, 쿠키 경로와 요청 출처 검증은 실제 웹/API 주소에 맞춰 결정합니다. 운영에서는 HTTPS를 사용하고 허용된 웹 출처만 접근시킵니다.

### 안드로이드

- 액세스 토큰은 메모리에 보관합니다.
- 리프레시 토큰은 기기에 암호화해 보관하고, 암호화 키는 Android Keystore로 보호합니다.
- 앱 재시작 시 유효한 리프레시 토큰으로 액세스 토큰을 다시 받습니다.
- 서버 JWT 서명 비밀키는 앱이나 웹에 배포하지 않습니다.

## 6. JWT 검증과 사용자별 접근 제한

JWT는 서명된 증표이며 기밀 정보 보관 수단으로 사용하지 않습니다. 비밀번호, 금융 내역, 외부 API 토큰을 JWT에 넣지 않습니다.

서버는 허용 알고리즘을 고정하고 서명, 만료 시각, 발급자, 사용 대상 및 필수 사용자·세션 식별자를 검사합니다. 토큰이 주장하는 알고리즘을 그대로 신뢰하거나 검증 없이 내용을 사용하지 않습니다. 계정과 세션이 유효한지도 검사합니다.

인증된 사용자는 본인의 데이터만 조회·수정·삭제할 수 있습니다. 서버가 인증에서 얻은 사용자 식별자를 기준으로 소유권을 확인하며, 클라이언트가 전달한 사용자 식별자를 신뢰하지 않습니다. 다른 사용자의 데이터 식별자로 요청해도 접근이 거부되어야 합니다. 실제 가계부 모델·API를 추가할 때에도 이 규칙을 적용합니다.

## 7. 사용자 기능과 저장 정보

서버는 회원가입, 로그인, 토큰 갱신, 현재 세션 로그아웃, 내 기본 정보 조회, 비밀번호 변경을 제공합니다. 비밀번호 변경은 현재 비밀번호 확인 후 수행하고 기존 세션을 모두 폐기하여 다시 로그인하게 합니다.

| 저장 대상 | 필요한 정보 |
| --- | --- |
| 사용자 | 내부 식별자, 정규화한 고유 아이디, 비밀번호 해시, 가입 시각 |
| 로그인 세션 | 사용자 식별자, 세션 식별자, 로그인·만료 시각, 폐기 상태 |
| 리프레시 토큰 관리 | 토큰 해시, 연결 세션, 교체·재사용 판정 정보 |
| 로그인 제한 | 정규화한 아이디 기준 실패 집계에 필요한 기록, 차단 종료 시각 |

이 표는 필요한 정보의 목록입니다. 실제 테이블 분리와 컬럼 구성은 구현 계획에서 정합니다. SQLite 파일에는 사용자 정보가 들어가므로 Git에 포함하지 않고 파일 접근 권한을 관리합니다.

## 8. 환경 설정

설정 우선순위는 **시스템 환경 변수 → 로컬 `.env` → 코드 기본값**입니다. 로컬 개발에서는 `.env`를 기본 설정 수단으로 사용합니다.

- JWT 서명 비밀키는 필수이며 누락되거나 안전 기준에 미달하면 서버 시작을 실패시킵니다. 임시 기본 비밀키로 대체하지 않습니다.
- SQLite 경로, 토큰 유효기간, 서버 주소·포트, 허용 웹 출처를 설정할 수 있게 합니다.
- 외부 API 토큰은 해당 기능에서 필요할 때 설정합니다. 이번 인증 기능을 위해 불필요한 API 토큰을 요구하지 않습니다.
- 설정값의 형식·범위를 시작 시 검사하고, 오류 안내에 비밀값을 노출하지 않습니다.
- `.env`와 실제 DB 파일은 Git에서 제외합니다. `.env.example`에는 설정 이름·설명과 비밀이 아닌 예시만 제공합니다.
- 비밀번호·토큰·서명 비밀키는 응용 프로그램 로그에 기록하지 않습니다.

## 9. 구현 완료 판단 기준

다음 동작을 자동 검증합니다. 이 목록은 향후 인증 구현의 인수 기준이며 현재 통과한 테스트 목록이 아닙니다.

1. 아이디 길이 경계, 허용 문자, 대소문자 무시 중복 검사가 동작합니다.
2. 비밀번호 8·20자는 허용 범위이고 7·21자는 거부됩니다. 두 종류 이상 조합, 특수문자 목록, 대소문자 구분과 공백·한글 거부가 동작합니다.
3. 회원가입·로그인·내 정보 조회·비밀번호 변경이 동작하며 비밀번호 원문이 저장되지 않습니다.
4. 로그인 실패 안내가 통일되고, 최근 5분의 실패 집계와 10회 도달 시 3분 제한이 경계 시각·동시 요청에서도 동작합니다.
5. 제한 중 성공 가능한 비밀번호도 거부하며, 추가 요청이 제한을 연장하지 않습니다. 성공·제한 해제 시 집계가 초기화됩니다.
6. 위조·만료·필수 항목 누락·잘못된 발급자·사용 대상의 JWT를 거부합니다.
7. 토큰 갱신·이전 토큰 재사용 감지·30일 절대 만료가 동작합니다.
8. 로그아웃은 즉시 적용되고 다른 세션은 유지됩니다. 비밀번호 변경 후에는 기존 세션 전체가 거부됩니다.
9. 사용자 A가 사용자 B의 데이터에 접근할 수 없습니다. 실제 데이터 API 구현 시 해당 API의 조회·수정·삭제에도 검증을 추가합니다.
10. 웹 쿠키 속성·CSRF 방어와 웹·안드로이드 토큰 전달 계약을 검증합니다. 실제 클라이언트의 저장소 동작은 각 클라이언트 구현에서 검증합니다.
11. 환경 변수 우선순위, 필수 설정 누락, 잘못된 설정의 시작 실패를 확인합니다.

프로젝트 파일 변경의 완료 검증은 [하네스 문서](../../harness.md)를 따릅니다. Ruff, pytest와 별도 `gpt-5.6-luna` 검토 결과를 보고하며, 실제 종료 훅 실행과 수동 검증을 구분합니다.
